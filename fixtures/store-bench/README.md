# store-bench

Benchmarks `use(store)` against context, Redux and Zustand, with and without the React Compiler.

**The claim under test:** with `use(store)` and the compiler, re-running only the components that read a store and letting the compiler bail out of unchanged work (and not subscribing to stores a component doesn't read this render) is cheaper than the selector model. In the selector model (react-redux `useSelector`, zustand), every mounted selector runs on every update.

The benchmark is also built to show where that claim fails: `store-single` puts all state in one store and reads it without selectors.

## Setup

1. Build React (experimental, production):

   ```
   yarn build --r=experimental --type=NODE_PROD
   ```

   The bundles alias `react`, `react-dom`, `scheduler` and `use-sync-external-store` to `build/oss-experimental`.
2. Install the libraries under test (this repo's tooling can't install them):

   ```
   cd fixtures/store-bench && yarn
   ```

   Variants whose libraries aren't installed are skipped at build time.
3. The React Compiler builds use `compiler/packages/babel-plugin-react-compiler/dist`. If it's missing or stale, run `yarn workspace babel-plugin-react-compiler build` from `compiler/`.

## Running

```
node build.mjs --count && node run-jsdom.mjs   # check the harness, no browser
node build.mjs --count && node run.mjs --verify # same DOM in every variant (Chrome)
node run.mjs --counts                           # renders and selector calls per update
node build.mjs && node run.mjs --smoke          # N=1k, no throttling, ~5 min
node build.mjs && node run.mjs --full           # full matrix + typing + memory, ~1h
node report.mjs                                 # results/report.md and report.html
```

The report's code examples are generated by `code-examples.mjs` from `src/apps/*.jsx` (instrumentation stripped), and the compiled `Row` comes from the same compiler build as the timed bundles, so they can't drift from what was measured. Any numbers in the report's prose are computed from the results, except `results/findings.html`, which is written by hand.

`run.mjs` drives your installed Google Chrome through Playwright (`--browser=chromium` uses Playwright's own Chromium, and `BENCH_BROWSER=/path/to/chrome` uses any build; `BENCH_SINGLE_PROCESS=1` runs the renderer in the browser process where renderer processes can't be launched). Filters:

```
--variants=store,redux   --scenarios=selection   --n=1000,10000
--compiler=on|off        --throttle=1,4          --iterations=200 --warmup=50
--restarts=3             --label=<name>          --dist=<dir>
--no-updates --no-typing --no-memory             (split a --full run)
```

`build.mjs` takes `--react=<dir>` (a frozen React build, e.g. `react-builds/head`), `--compiler=<file>` (a copy of the compiler's `dist/index.js`, so a `yarn build` can't change it mid-run) and `--out=<dir>`. Both are recorded in the dist's `build-info.json` and in every result file.

`--verify` replays 20 updates of every scenario (`--steps`) and compares the DOM hash after each one, then types into the filter and compares the DOM once the list has caught up.

For stable numbers, plug in the laptop, close other apps, and use `--full`. It randomizes the order and restarts the browser three times.

## Variants

| Variant | How state is read |
|---|---|
| `store` | `use(store)`, a store per entity plus small stores for selection, filter, expanded rows and details |
| `store-single` | `use(store)`, one store for everything, no selectors (worst case for stores) |
| `context` | `useReducer` at the root, one context |
| `context-split` | One context per slice of state, `memo` rows |
| `redux` | RTK `createSlice` + react-redux `useSelector` with inline selectors, `createSelector` for derived data |
| `zustand` | One `create()` store, a selector per component; the count is computed in render from two selectors |
| `zustand-granular` | Control: a zustand store per entity, so you can tell granularity apart from the store implementation |

Every variant is built with and without the React Compiler. Compiler builds use `panicThreshold: 'all_errors'`, so a component that fails to compile fails the build.

All variants render the same `RowView`/`CountView` components from `src/shared/views.jsx`, so the DOM is byte-identical. `run-jsdom.mjs` and `run.mjs --verify` check this. They differ only in how they read state.

## Scenarios

Each update runs inside `flushSync`, so every library renders synchronously at SyncLane and selector work during dispatch is counted.

Rows read the details in a child component (the idiomatic pattern for selector libraries) in every scenario except `details-inline`. The selector variants use a separate `RowWithInlineDetails` there, so the other scenarios don't charge them for an inline details selector they wouldn't write.

| Scenario | Update | What it isolates |
|---|---|---|
| `entity` | One entity's `x` | Granular stores re-render one row; selector libraries run every row's selector |
| `selection` | `selectedId` | **The core claim**: every row reads the selection. Stores re-render every reader and rely on compiler bailouts; selectors run N times and re-render 2 rows |
| `filter` | The filter text | Derived data per row and a derived count |
| `details-inline` | A details value read by 1% of rows, in the row itself | Conditional `use(store)` vs unconditional `useSelector` |
| `details-component` | The same, read in a child that only mounts when expanded | The idiomatic workaround for selectors, so this one should be a tie |
| `details-churn` | Expand every 10th row, then collapse them | Mounting and unmounting N/10 readers (subscribe/unsubscribe churn), plus every row reading the expanded state |
| `structure` | Add and remove an entity | List updates and subscribe/unsubscribe. Every variant re-renders every row (the list's elements are new) |
| typing (`--full`/`--typing`) | Type into the filter while 10k expensive rows re-filter | Transitions keep input responsive; uSES-based libraries render synchronously. Latency is keydown to the next frame; `settleMs` is until the list has caught up with the input |
| memory (`--full`/`--memory`) | Mount N rows | Mount time and heap bytes per row |

## Reading the results

- **Update cost.** The median and p95 ms per update, and the ratio to Redux (with the compiler when available).
- **Counters** (`--counts` or `run-jsdom.mjs`). `renders` counts renders of the components that call `countRender` (`src/shared/views.jsx`), not every component. In the main app those are `Row` (and `RowWithInlineDetails`), `RowView`, `DetailsView` and `CountView`; `App`, the list and `Details` aren't counted. `rows` is `Row` renders. `selectors` is selector calls. For example, `selection`:
  - `store` without the compiler re-renders 1000 rows and 1000 `RowView`s;
  - `store` with the compiler re-renders 1000 rows but only 2 `RowView`s, because the compiled `Row` returns its cached element;
  - `redux` is expected to run about 4000 selectors (4 per row) and re-render 2 rows.

  The timing is what decides whether 1000 bailed-out renders cost more or less than 4000 selector calls.

## Other suites

`--suite=<name>` on `build.mjs`, `run.mjs` and `run-jsdom.mjs` selects a suite from `src/redux-suite/suites.mjs`. Build each into its own directory with `--out` and run it with `--dist`, e.g.:

```
node build.mjs --suite=derived-selectors --count --out=dist-derived-count
node run-jsdom.mjs --suite=derived-selectors --dist=dist-derived-count   # same DOM, work per update
node build.mjs --suite=derived-selectors --out=dist-derived
node run.mjs --suite=derived-selectors --dist=dist-derived --throttle=1,4 --iterations=200 --warmup=50 --restarts=3
```

### Ported from react-redux-benchmarks

`src/redux-suite/` ports four scenarios from [reduxjs/react-redux-benchmarks](https://github.com/reduxjs/react-redux-benchmarks) (MIT), maintained by the Redux team. The `redux` variant keeps their code as written. Math.random() and Date.now() are replaced with seeded generators so every variant renders the same thing, and each update (one browser task) is timed in flushSync. State accumulates in these scenarios, so every variant runs a fixed number of steps per sample. The jsdom counts add `derivations`: runs of an expensive derivation (a `createSelector` result function, or the same computation in a component or selector).

| Suite | What it does | Scenarios |
|---|---|---|
| `derived-selectors` | 200 components read 500 posts and 1000+ comments through `createSelector`, 5 components share each category's stats | `mixed` (their 60/25/15 mix), `score`, `comment`, `role` |
| `rapid-dispatch` | 500 components; bursts of 1–9 dispatches per task, including an RTK listener cascade | `mixed`, `syncBurst`, `thunkBurst`, `listenerCascade` |
| `many-components-same-slice` | 5000 components read one counter | `increment` |
| `deeptree-nested-hooks` | 200 trees 15 deep, with counters at the leaves and textareas every 5 levels, driven by clicking buttons | `mixed` (their interval order) and one per button |

Each has `redux`, `store` (idiomatic `use(store)`) and `zustand` variants. `derived-selectors` also has `store-memo`, the recommended pattern for shared derived data (a userland `weakMemo`, `src/redux-suite/derived-selectors/shared-memo.js`), and `store-derived`, a workaround that computes the shared derived data once per update in the action (it tears under transitions; reference only). `derived-selectors-spike` adds the other options from `docs/use-store/research/shared-derived-data.md` and 20 or 50 readers per category (`-k20`, `-k50`).

Without the compiler, the `store` variants recompute every derived value on every render (there's no `useMemo`), while Redux keeps `createSelector`. Those builds show what the compiler buys, not how someone would write the app without it. The `zustand` variant runs its derivations unmemoized in selectors, as its docs show, so it pays for them on every update.

### Controls and sweeps for the main scenarios

| Suite | Variants |
|---|---|
| `fairness` | `redux`, `redux-plain` (hand-written reducer, no RTK or Immer), `redux-nofreeze` (Immer auto-freeze off), `store`, `zustand` |
| `typing` | `redux-deferred` and `zustand-deferred` read the filter through `useDeferredValue`. Run with `--typing`; there are no update scenarios |
| `sweeps` | `sweep-*.jsx` for store, store-keyed (selection through a `weakMemo`'d store per row), redux and zustand: `cX-wY` compiles X% of rows (the rest are `'use no memo'` copies) and renders rows with Y props. Entity and selection only. Only `c100-w8` is also built without the compiler (the 0% point); `run.mjs --verify` compares bundles within a width |

## Caveats

- RTK uses Immer with auto-freeze, which is its documented default. That cost is part of idiomatic Redux.
- `context-split` uses `memo` on rows, as people do. With the compiler, `memo` is redundant but harmless.
- jsdom timings aren't meaningful. Use Chrome.
