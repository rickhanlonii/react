# Plan 1: Fix client manifest generation (bundler responsibility)

## Status: Deferred — pending turbopack conversion investigation

## Problem

`server.js:32` and `ssr-server.js:43` both hardcode `var components = ['Counter', 'TextInput']`. Adding a new `'use client'` component requires manually updating two arrays in two servers — easy to forget, results in silent failure (Flight error rows that get swallowed).

The client manifest and SSR module map are the **bundler's** responsibility. In a real framework, the bundler discovers `'use client'` directives during compilation and generates the manifest automatically. This project uses esbuild but has no plugin to handle client component discovery.

## Current state

- **Flight server** (`server.js`): `buildClientManifest()` builds manifest entries mapping `file://` URLs → `{id, chunks, name}`. Passed to `renderToPipeableStream()`.
- **SSR server** (`ssr-server.js`): `buildSSRModuleMap()` builds module map mapping IDs → `{id, chunks, name}`. Used by the Flight client during SSR to resolve `I` rows.
- **Module endpoint** (`server.js:/modules/:file`): Already serves ANY `.jsx` file from `src/components/` on demand — not restricted to the hardcoded list.
- **`node-register`**: Creates client reference proxies with `$$id = url.pathToFileURL(filename).href`.

## Requirements

The manifest must be generated by the bundler, not hardcoded. It must:
1. Discover all `'use client'` files automatically
2. Produce the correct manifest format for `renderToPipeableStream` (keyed by `file://` URL)
3. Produce the correct SSR module map format (keyed by module ID)
4. Update when new client components are added (at minimum on server restart, ideally on file change)

## Quick fix (interim)

Replace hardcoded arrays with filesystem discovery:
```js
var components = fs.readdirSync(componentsDir)
  .filter(f => f.endsWith('.jsx'))
  .map(f => f.replace('.jsx', ''));
```
This is a stopgap — proper solution requires bundler-generated manifests.
