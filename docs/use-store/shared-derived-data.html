Shared derived data with use(store)

Options for sharing an expensive derivation between components, with code and measurements · React core · October 31, 2026

use(store) has no selectors. Components read store values with use() and derive whatever they need in plain code, and the React Compiler memoizes those derivations. But the compiler memoizes per component instance. When K components derive the same expensive value from the same store values, they compute it K times. Redux's createSelector computes it once. This page covers the six ways to fix that, which ones are correct under concurrent rendering, and what each would cost in API.

Short version. Store values are immutable snapshots, and every component in a render reads the same snapshot object. So a cache keyed on the identity of its arguments is correct under concurrency by construction: two renders at different points in time read different snapshots and use different keys. Options 3–6 all reach Redux's derivation count and beat it. The recommendation is a React-owned client cache() scoped to a render, with the compiler as an optional accelerator. Computing derived values in updates (option 2) is fast but tears under transitions, and no API for reading stores outside render fixes that.

The constraint: correctness under concurrency

Any answer has to stay consistent while React renders a transition in the background and commits urgent updates over it. Two facts make sharing safe:

Snapshots are immutable

Every store.update() produces a new value. A derivation keyed on the identity of its inputs can never return a result computed from different data.

One cut per render

Every component in a render reads every store at the same point (lanes plus a global update sequence number), and gets the same snapshot object. So all K readers in a render hit the same cache entry, and a concurrent render at a different cut uses different keys.

That holds for any derivation that runs during render, from values read with use(). It doesn't hold for a derivation that runs outside render.

2 · Compute in the update tears

Compute the derived value once in the action, and keep it in its own store. It's the fastest variant, which is why it's tempting.

The actionsapps/store-derived.jsx
const latest = {posts, comments};↑ a userland copy of the latest values, outside Reacts = {  users: createStore(users),  posts: createStore(posts),  comments: createStore(comments),  categoryStats: createStore(getAllCategoryStats(posts, comments)),};let commentId = comments.length;const actions = {  updateScore(id, score) {    const next = latest.posts.slice();    next[id] = {...latest.posts[id], score};    latest.posts = next;    s.posts.update(next);    s.categoryStats.update(↑ computed from the latest values, not from what a render sees      getAllCategoryStats(next, latest.comments),    );  },  addComment(postId, userId) {    const comment = {      id: commentId,      postId,      userId,      text: `Comment ${commentId}`,    };    commentId++;    latest.comments = [...latest.comments, comment];    s.comments.update(latest.comments);    s.categoryStats.update(      getAllCategoryStats(latest.posts, latest.comments),    );  },};
It tears. The derivation runs on the latest values, including a transition that hasn't committed. When an urgent update commits while a transition is pending, the derived value includes the transition's data but the rest of the UI doesn't. This test, now in ReactUseStore-test.js, passes on the current build, so the tear is real:

Correctness
Wrong under transitions. Fixing it means putting the sources and the derived value in one store with one reducer, which gives up granularity.
Ergonomics
A mutable copy of the latest values in userland, and a second update in every action that touches a source. A read-outside-render API would remove the copy, but not the tear.

3 · Userland shared memo correctworks today

Wrap the derivation in a memo keyed on argument identity, at module scope. It works today with reselect's weakMapMemoize; no createSelector needed.

Usageapps/store-memo.jsx

The memoshared-memo.js
function createNode() {  return {    hasValue: false,    value: undefined,    objects: null,    primitives: null,  };} function getNode(root, args, from) {  let node = root;  for (let i = from; i < args.length; i++) {    const arg = args[i];    let next;    if (      typeof arg === 'function' ||      (typeof arg === 'object' && arg !== null)    ) {      let objects = node.objects;      if (objects === null) {        node.objects = objects = new WeakMap();      }      next = objects.get(arg);↑ snapshots are WeakMap keys, so entries die with their snapshot      if (next === undefined) {        next = createNode();        objects.set(arg, next);      }    } else {      let primitives = node.primitives;      if (primitives === null) {        node.primitives = primitives = new Map();      }      next = primitives.get(arg);      if (next === undefined) {        next = createNode();        primitives.set(arg, next);      }    }    node = next;  }  return node;} function weakMemo(fn) {  const root = createNode();  return function () {    const node = getNode(root, arguments, 0);    if (node.hasValue) {      return node.value;    }    const value = fn.apply(null, arguments);    node.hasValue = true;    node.value = value;    return value;  };}
Correctness
Correct by construction (identity keys).
Memory
Fine when the snapshots are object arguments: entries die with them. Leaks when a long-lived object is followed by a changing primitive (search(LIST, query)) or for primitive-only calls (1.6 MB per 10k values). reselect warns about this in dev.
API
None in React. Users have to know to do it.
Risks
The cache is module-global (shared across roots, tests and SSR requests). An impure function (one that reads a locale or Date.now()) returns stale results to newly mounted components. One result object is shared by every reader.

4 · A React-provided client cache() correctrecommended

React exports cache(), but only the server version shipped, and it's scoped to a request. Client caching was removed in 2024 because its lifetime was undecided (#27977). disableClientCache is on everywhere, and the <Cache> element was removed too (#28698). The proposal here doesn't revive that design. It's a render-scoped root from a new dispatcher method (getRenderCache(), reset in prepareFreshStack), with no <Cache> boundary, CacheContext, getCacheForType or refcounting. That gives one rule for both server and client: cache() dedupes calls within a render. It's close to the "render's contextual cache" in Seb's "Cache without Signals" (reactwg #72), and derived data from stores is the "CPU based memoization" use case from "Global Memo === Cache" (#53).

5 · Compiler-emitted sharing correctneeds a heuristic

The compiler already memoizes the call per instance, which already assumes the function is pure. The change: keep the per-instance check, and go to a shared cache only when this instance's inputs changed. Hand-edited compiler output, measured:

Compiled CategoryStats with a shared callapps/store-compiled-shared.jsx
function CategoryStats(t0) {  const $ = _c(14);  const {category} = t0;  const posts = use(s.posts);  const comments = use(s.comments);  let t1;  let t2;  let t3;  let t4;  let t5;  if ($[0] !== category || $[1] !== comments || $[2] !== posts) {↑ the per-instance check stays in front    // SHARED    const stats = _sharedCall(getCategoryStats, posts, comments, category);↑ was getCategoryStats(...): only reached when this instance missed    t1 = category;    t2 = ': ';    t3 = stats.postCount;    t4 = ' posts, avg ';    t5 = stats.avgScore.toFixed(1);    $[0] = category;    $[1] = comments;    $[2] = posts;    $[3] = t1;    $[4] = t2;    $[5] = t3;    $[6] = t4;    $[7] = t5;  } else {    // ...read the cached slots  }  // ...

Which calls qualify. The compiler already knows most of what it needs:

  • the callee is a module-scope or imported function;
  • every argument is frozen (use() results, props) or primitive;
  • the result isn't mutated after the call;
  • at least one argument is a reactive object.

The catch: the compiler can't see cost or sharing. A lookup costs 30–80 ns. That's noise against a 15 µs derivation, but it adds up across cheap calls. Routing unshared calls through the cache costs about 7% at steady state on this benchmark. A default-on pass needs an opt-in (a cache()-wrapped callee) or an adaptive runtime that turns off call sites that never hit:

// Sketch of the runtime a compiler pass would target (not implemented).// One cache per call site, scoped to a render, that turns itself off when// the call site isn't shared.function createSharedCallSite(fn) {  let hits = 0;  let misses = 0;  let direct = false;  return function () {    if (direct) {      return fn.apply(null, arguments);    }    const node = getRenderCacheNode(fn, arguments); // reset each render    if (node.hasValue) {      hits++;      return node.value;    }    if (++misses > 64 && hits < misses / 4) {      // Expensive but never shared (like getCommentCount here): stop      // paying for the lookup.      direct = true;    }    node.hasValue = true;    return (node.value = fn.apply(null, arguments));  };}

Problem

The compiler-emitted variant was timed with 30 warm-up updates, so its mixed numbers include JIT warm-up of the cache path. At steady state it's about 7% slower than the userland memo there, because unshared calls go through the cache. Option 2 is struck through because it isn't correct.

Recommendation

  1. Drop "compute in the update" as a pattern. It tears, and no API fixes that.
  2. Make sharing a React-owned client cache(), scoped to a render.
    • It's correct per root and bounded in memory for any arguments.
    • It can't go stale for new mounts, and it matches the server's per-request semantics.
    • It adds no new concept to the store API.
    Two generations are the fallback.
  3. Use the compiler as the accelerator, not the decider. Keep its per-instance check in front of cache(). Prototype an automatic, adaptive pass behind a flag and measure it on a real app.
  4. No derived stores in v1.

Decisions

  • Is cross-component sharing React's job (a client cache()) or userland's (document weakMapMemoize)? Userland performs the same today.
  • If it's React's job, which lifetime, and is reusing the name cache with a client lifetime acceptable? It also needs a Fizz implementation.
  • Fund the compiler experiment, and on which app?
  • Close the door on derived stores for v1?
