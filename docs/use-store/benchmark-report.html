use(store) + the compiler vs selectors

Benchmark results · October 30, 2026 · Apple M4 Max · darwin 27.0.0

Selector libraries decide what to re-render by running every mounted selector on every update. use(store) does the opposite: every component that reads a changed store re-renders, and the React Compiler makes the ones whose output didn't change return their cached element. The claim is that the second model is cheaper. Below, the same app is built 7 ways and timed with and without the compiler.

Short version. In the main benchmark, with the compiler, use(store) matched or beat the faster of Redux and Zustand in every scenario, at every size and CPU speed: 35 of 36 configurations faster, 1 tied, 0 slower. That includes selection, the case selectors are built for (one value read by every row, two rows change): up to 1.5× faster (5 faster, 1 tie) vs the faster library. Getting there took a general reconciler optimization, behind a flag, that lets a compiled component that returns its cached element skip reconciling it (without it, selection is 1.2× slower to 1.2× faster (1 faster, 5 slower)). It doesn't win everywhere, and the caveats list where: rows that select only 2 values (selection 1.3–1.4× slower vs Zustand); partially compiled apps; expensive derived data shared by many components (up to 1.2× slower (1 tie, 5 slower) vs Redux, fixable with a shared cache). The compiler is required: without it, use(store) loses fan-out reads badly.

Selectors: cost scales with what's mounted

  • Every useSelector runs on every dispatch, so react-redux can decide whether its component re-renders. With 1,000 rows that's about 5,000 calls per update, whatever changed.
  • Hooks can't be conditional, so a row that isn't expanded still subscribes to details and selects null on every update.
  • Derived values need a selector, often a memoized one, to avoid re-rendering.

use(store): cost scales with what changed

  • Only components that read the changed store re-render. A store per entity means an entity edit re-renders one row.
  • use() can be called conditionally, so rows that aren't expanded never subscribe to details.
  • Derived values are plain code. The compiler memoizes them, and it caches the JSX on the values it depends on.

What the compiler does with that Row

The real compiler output for the store Row (the same build the timed bundles use). When the selection changes, every Row re-runs. The reads are cheap, because each store's value is computed once per render for the whole root, not once per component. Then 8 comparisons run, and 998 of 1,000 Rows return $[14] without rendering RowView. That bailout is the entire trick.

Caveats, and where it doesn't win

  • Shared expensive derived data. In the Redux team's derived-selectors benchmark, plain use(store) is up to 1.2× slower (1 tie, 5 slower) vs Redux. Five components share each expensive result: createSelector computes it once, while the compiler memoizes per component, so use(store) computes it five times. A cache keyed on store snapshots (correct under concurrency, since snapshots are immutable) fixes it: the fastest correct sharing option is 1.5–1.9× faster vs Redux. That cache is an API decision, not an implementation detail.
  • Selection depends on how many values each row selects. The main suite's rows read 4 stores (5 selectors in Redux and Zustand). In the sweeps, rows read only 2 (entity and selection), so the selector libraries run just 2 cheap selectors per row, and selection is 1.3–1.4× slower for use(store) vs the faster library (4 props: 1.2–1.3× slower; 16 props: 1.3–1.4× slower). When every row reads a changed value that almost never changes its output, a few cheap selectors are cheaper than re-running each row and bailing out. Entity edits stay 2.7× faster.
  • Partial compiler coverage hurts fan-out reads a lot. With 90/75/50% of rows compiled, selection is 3.0–3.4× slower / 5.7–5.9× slower / 9.8–10× slower for use(store) vs the faster library, because each uncompiled row re-renders its whole subtree. Entity edits don't care (2.4–2.5× faster at 50%).
  • The compiler isn't optional for fan-out reads. Without it, use(store) is 3.2–6.0× slower than Redux on selection (both without the compiler), because every Row re-renders RowView too. Without the compiler, treat use(store) as a granular-store API.
  • The selection result depends on enableSameElementBailout, a general reconciler change (behind its own flag, full test suite green, in review). Without it: entity edit 2.7–8.9× faster; filter 1.7–2.6× faster; selection 1.2× slower to 1.2× faster (1 faster, 5 slower), vs the faster of Redux and Zustand. It speeds up every compiled re-render, context included, so it isn't store-specific.
  • Compiled context is faster on filter in some configurations (1.3× slower to 1.1× faster (3 faster, 2 tie, 1 slower)): context re-renders the same rows with one useContext each, while the store Row makes four use() calls. Context can't do the granular cases (entity, conditional reads, list changes), where use(store) is far ahead.
  • Memory. At the largest size, use(store) uses 2,850 bytes per row, vs context 2,166, zustand 5,144, redux 8,446.
  • Single-process headless Chromium on a laptop with background load; every timing was gated on load and taken in interleaved restarts. Ratios between variants are what matter, not absolute numbers.

Scenario by scenario

Why each scenario comes out the way it does. The numbers are in the scoreboard above and the charts below; the work counts come from the counting build.

Selection: the selectors' best case

Every row reads the selected id, and only 2 rows change.

  • Selectors: about 5 selectors per row run on every update (about 5,000 at N=1k), and 2 rows re-render.
  • use(store): all N Rows re-render. Each re-reads its stores from a per-root cache (computed once per render, not per component), compares its 8 memoized values, and 998 of 1,000 return the cached element.
  • The same-element bailout (a flagged reconciler change) makes that last step cheap: a component that returns the exact element it rendered last time skips reconciling its child. With it, a bailed-out Row costs less than five selector calls; without it, they're about even.
  • Without the compiler every Row re-renders RowView too, and use(store) loses badly. This scenario is why the compiler is required.

Entity edit: cost scales with the change

One entity changes.

  • With a store per entity, use(store) re-renders one row and runs nothing else. Selector libraries run every row's selectors to find that row, so the gap grows linearly with N.
  • The control: zustand-granular (a Zustand store per entity) comes within about 10–25% of use(store). So this win comes from granular stores, which are the natural way to write use(store), and which keep working with transitions.

Conditional reads: what selectors can't do

1% of rows are expanded and read a frequently updated value.

  • Inline: use(s.details) inside if (expanded), so only the 10 expanded rows subscribe. The selector libraries render the same 10 rows, but also run every row's selectors, because hooks can't be conditional. Identical renders, about 5,000 extra selector calls: the cost of selectors, isolated.
  • Child component (the standard workaround) doesn't help selector libraries: the other selectors in every row still run on every dispatch.

Typing during a transition

Keystrokes while 10k expensive rows re-filter.

  • use(store) updates are lane-aware, so the list re-filters in a transition and the input stays responsive.
  • useSyncExternalStore renders external-store updates synchronously even inside startTransition, so Redux and Zustand block on the whole re-filter.
  • useDeferredValue is their idiomatic workaround and removes most of that tail (see the typing table under "More scenarios"); use(store) gets it without restructuring.

Derived data (filter)

Half the rows change. Selector libraries re-run their filter selectors in every row; use(store) re-renders the rows and the compiler memoizes the derivation per row. Compiled context is close here, since it does the same re-render with one read per row.

List changes

Adding or removing a row re-renders the list in every variant; the selector libraries also pay for every row's selectors on each dispatch.

Memory and mount

use(store) keeps one small read list and one subscription per component, with no per-read hook slot. It uses less memory per row than the selector libraries and somewhat more than context; see the table below.

Every final number comes from load-gated, interleaved restarts on the final build (react-builds/final); any run where the machine's load spiked was discarded and re-run.

Methodology

  • Variants.
    • store: a store per entity, plus small stores for shared state.
    • store-single: one store, no selectors (the worst case for stores).
    • context: useReducer at the root, one context.
    • context-split: one context per slice, memo rows.
    • redux: RTK createSlice, react-redux useSelector, createSelector.
    • zustand: one store, a selector per component.
    • zustand-granular: a store per entity (a control for granularity).
    Every variant renders the same shared RowView, and the DOM was verified byte-identical across all 14 bundles in every scenario.
  • Compiler. babel-plugin-react-compiler from this repo with panicThreshold: 'all_errors', so every component in every variant was compiled.
  • Timing. Each update runs in flushSync. Updates are timed in batches of at least 5 ms, and each batch is divided by the number of updates in it. That's 200 samples after 50 warm-up updates, in a fresh browser per configuration, in randomized order, 42 times. Chromium's CPU throttling is used for the 4× runs.
  • Typing. Playwright types with a 50 ms delay. Latency is measured from keydown to the first frame after it.
  • Memory. CDP HeapProfiler.collectGarbage and Runtime.getHeapUsage, before and after mount.
  • Versions. react 0.0.0-experimental-a703ca64-20261030 · redux 5.0.1 · react-redux 9.3.1 · @reduxjs/toolkit 2.13.0 · zustand 5.0.16 · node v25.4.0
Caveats.
  • This ran in headless Chromium in single-process mode (the renderer runs on a thread of the browser process), because the environment doesn't allow launching renderer processes. V8 and React do the same work, so the comparisons between variants hold, but absolute numbers may differ from regular Chrome.
  • Without cross-origin isolation the timer resolution is 100 µs. Batching keeps that to a couple of percent per sample.
  • RTK's Immer auto-freeze is on, which is its documented default.
  • Rows aren't wrapped in memo except in context-split, so list changes re-render rows in every variant.
  • The workload is synthetic: an entity list with fixed render work per row. Real apps will vary. The work counters show how the costs scale.
