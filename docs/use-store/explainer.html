use(store): global state that understands concurrency

A store you create once and read anywhere, conditionally, with use(). It follows the same rules as useState, including transitions, rebasing, Suspense, Activity and hydration. It only re-renders the components that read it. 

import {use, unstable_createStore as createStore, startTransition} from 'react';

const cart = createStore([]);

function CartBadge() {
  return <Badge count={use(cart).length} />;   // re-renders only when the cart changes
}

function addToCart(item) {
  cart.update(items => [...items, item]);         // urgent, like setState
}

startTransition(() => cart.update(loadSavedCart)); // or a transition, no tearing

The problem we've had for years

State that no single component owns has no good answer in concurrent React.

slow Context + useReducer

Correct with transitions, but every consumer re-renders on every change. Teams split providers, build workarounds, or avoid context altogether. Compiled context selectors were tried in production and came back inconclusive (#322).

de-opts useSyncExternalStore

Fast and tear-free, but a store update can never be a transition. Updates inside startTransition render synchronously and show Suspense fallbacks. That rules out the features we built concurrency for.

fragile Userland concurrent stores

Jordan's prototype (#387) and Justin's ponyfill get close, but they need React internals (__CLIENT_INTERNALS…T), a layout-effect "fixup" that renders twice, and the assumption that every transition is entangled.

What the ecosystem has told us: "We've repeatedly gotten asked 'when will React-Redux be concurrent compatible?', and our answer has always been 'when the React team gives us the primitive we need.'" (Mark Erikson, on facebook/react#35449)

The API: three things

Shaped like useState, but shared, and read with use().

// 1. Create it anywhere: module scope, a parent component, a context value.
const count = createStore(0);
const todos = createStore(initialTodos, todosReducer);   // optional fixed reducer

// 2. Update it anywhere: events, effects, async actions, outside React.
count.update(1);                // a value
count.update(c => c + 1);       // or an updater, like setState
todos.update({type: 'add', text});  // or an action, with a reducer

// 3. Read it while rendering. Conditionally, in loops, nested in other use() calls.
const value = use(count);

Why use() and not useStore()

use takes no hook slot. You can read a store inside an if, a for loop, or right after an early return, like use(context). Seb's original use post (#52) listed stores as one of the reasons use exists: use<T>(Context<T> | Promise<T> | Store<T>).

Why no selectors

Selectors don't compose with custom Hooks and move logic out of components (#155, #296). Instead: re-render only actual readers, bail out when the value is unchanged, use granular stores (a store per entity, or stores of stores), and let the compiler memoize everything downstream of the read.

How it differs from Context

Context passes values down the tree. A store is a value that lives outside the tree that any component can read.

How it works

The trick: it's the useReducer update queue, moved from each component to each root.

1 · Updates

store.update(action) asks each root's record for a lane, the same way setState does: transition, discrete, or default. It appends {lane, action, seq} and schedules only the subscribed readers. If nothing is pending and the value doesn't change, it bails out without rendering.

2 · Reads

use(store) applies the updates included in the render's lanes and skips the rest, the same as useState. If it skipped any, it merges their lanes into the fiber, so a component that mounts mid-transition re-renders with that transition. There's no fixup render or effect.

3 · No tearing, ever

Every update gets a monotonic seq. A render records the seq when it starts and ignores anything newer. That's how React already hides concurrent setState calls from an in-progress render, so two components in one render can never see different versions. There's no consistency check and no sync de-opt.

4 · Commit

At commit, each record folds the lanes that just committed into its base state. Updates that were skipped stay in the queue, and later updates stay too as NoLane clones, so the next render rebases them in order. That's the useReducer algorithm, and the reducer doesn't run again when the render already computed the result.

5 · Subscriptions without a hook slot

use(store) pushes an internal insertion effect onto the fiber's effect list. That gives us cleanup on unmount and conditional reads for free. Hidden Activity trees stay subscribed, so they update in the background at offscreen priority.

6 · Server and hydration

The value a store was created with is its server snapshot. Fizz renders it and the client hydrates with it, so there's never a mismatch. Readers then catch up to the latest value, the same model as getServerSnapshot but with no extra API.

Use cases

Things that are awkward or impossible today, and are a few lines with stores.

App-wide state without the provider tax

export const theme = createStore('light');

function ThemeToggle() {
  const current = use(theme);
  return <button onClick={() => theme.update(t => (t === 'light' ? 'dark' : 'light'))}>{current}</button>;
}
// No Provider. Only ThemeToggle and other readers re-render.

Fine-grained lists with stores of stores

const todos = createStore([]);   // a store holding stores

function TodoList() {
  return use(todos).map((todo, i) => <Todo key={i} todo={todo} />);
}
function Todo({todo}) {
  const {text, done} = use(todo);
  return <li onClick={() => todo.update(t => ({...t, done: !t.done}))}>{text}</li>;
}
// Toggling one todo re-renders one <Todo>, not the list. No selectors, no memo.

Navigation as a transition, from outside React

const route = createStore('/');

// A router can update the store from a popstate listener...
window.addEventListener('popstate', () =>
  startTransition(() => route.update(location.pathname)),
);

function Router() {
  const path = use(route);
  return <Suspense fallback={<Spinner />}>{matchRoute(path)}</Suspense>;
}
// ...and the old page stays on screen while the new one suspends, with no
// fallback flash. useSyncExternalStore can't do this: it de-opts to sync.

Conditional and dynamic reads

function Dashboard({widgets, user}) {
  if (!user) return <Login />;                 // early return before reading: fine
  let unread = 0;
  for (const w of widgets) unread += use(w.unreadStore);   // loops: fine
  return <Header unread={unread} />;
}
// Subscriptions follow whatever the last render read. Stores that are no longer read are unsubscribed at commit.

Async actions and forms batch correctly

const cart = createStore([]);

async function checkout(formData) {        // <form action={checkout}>
  cart.update(items => items.map(markPending));
  await submitOrder(formData);
  startTransition(() => cart.update([]));
}
// Updates before and after the await commit together when the action finishes,
// exactly like setState inside an action. (Verified side by side in the copies.)

Readers that mount mid-transition don't tear

startTransition(async () => {
  filter.update('done');
  await slowSearch();
});
// While that's pending, a sync update reveals a new <FilterLabel> that reads `filter`.
// It mounts showing the OLD filter, matching every other reader on screen,
// and switches to 'done' in the same commit as everyone else when the transition lands.

SSR that just works

// Shared module. The same code runs on the server and in the browser.
export const prefs = createStore(window.__PREFS__ ?? defaultPrefs);

// The server renders the initial value. The client hydrates with the same value, so
// there's no mismatch. If prefs changed before a boundary hydrated, it hydrates
// first and then re-renders. No getServerSnapshot.

A foundation libraries can build on

// The kind of thing Redux/Zustand/Jotai could ship on top: concurrency-safe, no internals.
export function createSlice(initial, reducers) {
  const store = createStore(initial, (state, {type, payload}) => reducers[type](state, payload));
  const actions = Object.fromEntries(
    Object.keys(reducers).map(type => [type, payload => store.update({type, payload})]),
  );
  return [store, actions];
}

Semantics: what you get, and what's different

The default is "behaves like useState". The differences are deliberate, and each one is pinned by tests.

same as useState

  • Batching with other updates in the same event
  • Transitions, entanglement, rebasing order
  • Async actions: suspends until the action finishes
  • flushSync, useDeferredValue, Suspense, Activity
  • Eager state: an idle store computes the next state at dispatch
  • StrictMode double-invokes reducers
  • "Not wrapped in act()" warnings
  • Reducer errors throw during render, where error boundaries catch them
  • Controlled inputs stay in sync

different, on purpose

  • Survives remounts. It's not component state.
  • Shared by every component and root that reads it.
  • Updating during render warns ("Cannot update a store while rendering…"), because a store is shared, so it's a side effect. The update renders after the current render.
  • No "unmounted component" warnings: an update isn't tied to a component.
  • The server renders the initial value, and clients catch up after hydration.
  • The reducer is fixed at creation (it can't close over props), which is what lets every root replay updates.
  • Bails out at dispatch when nothing is pending and the value doesn't change, so it renders less than useState.

Why ship it

It closes the oldest gap in concurrent React

Transitions, Suspense, Activity and View Transitions only work as well as the state that feeds them. Today, the moment state lives outside a component, you choose between fast (uSES) and concurrent (context). This removes that choice.

It's small and reuses proven machinery

Under 900 lines in the reconciler, comments included: one new module plus small hooks into the hooks file and work loop. The core is the useReducer queue algorithm, the concurrent-update seq model, and insertion effects. Nothing here is a new scheduling concept, and with enableStore off none of the new code runs.

It unblocks the ecosystem

Libraries can get concurrent compatibility by building on a primitive instead of reverse-engineering internals. It also gives userland ponyfills a target to converge on.

It makes the compiler story true

"No selectors, the compiler will handle it" was missing the primitive that makes reads fine-grained. With per-store subscriptions, granular stores, and compiler memoization downstream of use(), it now has one.

Proposed rollout

  1. Land behind enableStore: __EXPERIMENTAL__ in OSS, __VARIANT__ in www. It's already wired up that way.
  2. Dogfood in www on a store-heavy surface (a Recoil or context-selector replacement), and measure renders and interaction latency against context and uSES.
  3. Publish the RCP update with these semantics, then ship to experimental for library authors (Redux, Zustand, Jotai, TanStack, Relay).
  4. Follow-ups: optimistic stores (with #416), DevTools store editing and hook names, external-source interop and observables (#403).

Honest open questions

  • Cross-root consistency isn't guaranteed: a new root starts from the latest value (Seb's position in #403). React Native's multi-surface direction (one root plus portals) avoids this.
  • "Derive state during render" doesn't carry over to stores. It warns, by design.
  • Performance is measured on synthetic benchmarks, not yet on a real app. See benchmark-report.html. With the compiler, use(store) matched or beat the faster of Redux and Zustand in every configuration of the main benchmark, and won three of the Redux team's own four benchmarks. Where it doesn't win:
    • rows that select only one or two values, where a few cheap selectors beat re-running each row (selection is 1.3–1.4× slower than Zustand);
    • partially compiled apps;
    • expensive derived data shared by many components, which needs a shared cache.
    The selection result also relies on a separate reconciler optimization (enableSameElementBailout). Real-world numbers still need the www experiment.
  • Shared derived data needs an answer. A cache keyed on store snapshots is correct and fast (spike). Computing derived values in updates tears under transitions.
