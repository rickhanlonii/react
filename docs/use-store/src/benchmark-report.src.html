What the comparisons mean

The claim I'm testing: with the compiler, re-rendering only the components that read a changed store costs less than running every mounted selector on every update. Selector libraries like react-redux and Zustand subscribe each component with a selector. Every selector runs on every update to decide whether its component re-renders. use(store) has no selectors. A store update re-renders the components that read that store, and the compiler skips the parts of their output that didn't change.

The headline compares use(store) with the compiler against the faster of Redux and Zustand in each configuration, with each library at its own faster compiler setting. A configuration is one scenario at one list size and one CPU speed. The counting build that explains each result runs at rows. The other comparisons are against each library on its own, against Context, and against a granular control (Zustand with a store per entity).

  • Editing one entity re-renders one row instead of running a selector in every row (). Adding or removing a row is , and conditional reads are .
  • It loses when the selection changes: . Every row reads the selected id, so every row re-renders, while selectors re-render only the two rows whose selection changed. The selection section explains why, and shows the pattern that wins.
  • The granular control has its own column (it isn't part of the headline). It puts each entity in its own Zustand store, to show how much of the win comes from granularity alone. use(store) loses of configurations to it, mostly on selection.

Two things aren't in the headline. Keyed selection, the recommended pattern for selection, is measured in the sweeps, not the main benchmark. The build without the same-element bailout has its own section.

Why

With use(store), every row re-renders, the compiler returns the cached RowView element for all but two of them, and the same-element bailout skips reconciling it. Zustand re-renders two rows, but it runs every row's selectors to find them. The verdict is .

A CPU profile splits the cost per row. It was taken on the previous build, on the same case in the sweeps (below), where each row reads two stores. Visiting the row's fiber costs about the same either way, because Zustand's rows are cloned and bail out, and the store rows re-render and skip their children. The difference is the component itself. Running a compiled row, even one that returns its cached element, costs more than a couple of cheap selector calls. In that profile, removing all of the store's own work (the reads, comparing them, and marking readers) would only bring it to about a tie. Store-side trims measured on that build were too small to keep, so I reverted them. When each row reads only one or two values, I don't think a store-side optimization changes this.

The fix: keyed selection

Instead of every row reading the selected id, each row reads a store that says whether it's selected. The stores are created on demand by weakMemo, the helper from shared derived data. Selecting a row updates the old row's store and the new row's store, so two rows re-render. It's the store version of a keyed selector, like Solid's createSelector, and the explainer has a sandbox for it.

That's the cost of partial compiler coverage - a reader the compiler doesn't cover re-renders its children, unless you memoize them by hand. With keyed selection, coverage doesn't matter, because only two rows render.

Two design changes could close the gap for unkeyed selection, and neither is implemented. The compiler could emit a small check next to a component that says whether its output changes for new store values. React could then run the check instead of the component. Or React could re-run only the memoized blocks that depend on the changed reads. Both are changes to the compiler and the reconciler, not to the store.

Why every reader computes it, and the options

The problem: memoization is per component

Redux shares derived data with createSelector: the selector caches its result, and every component that uses it gets the same one. use(store) has no selectors. The compiler memoizes a derivation per component instance, so each reader computes it once per snapshot, and when the stores change, every reader computes it again.

The derived-selectors benchmark from react-redux-benchmarks shows this. Each category has components that show stats computed from every post and comment. On a score update, Redux runs the expensive derivation an average of times, and plain use(store) runs it times. The spike raises that to readers per category to see how the cost grows. With the most readers, a score update costs derivations with plain use(store) and still with Redux.

The constraint: correct under concurrency

Two things let a shared derivation stay correct under concurrency:

  • Store values are treated as immutable snapshots, like state. An update replaces the value, so a derivation cached by the identity of its inputs can't return a result computed from other data. Mutating a store value in place breaks this, the same as with useState.
  • Within a root, every component in a render reads every store at the same point and gets the same snapshot object. So every reader in a render hits the same cache entry, and a concurrent render at a different point uses different keys.

Computing the derived value in the update instead, and putting it in its own store, looks faster, but it tears (see no tearing in the explainer). The derivation runs on the latest values, not the ones a render reads. Take a pending transition on one store and an urgent update on another. The urgent commit shows stats that include the transition's data next to rows that don't. spike-shared-derived/concurrency.mjs reproduces it with the real reconciler. It's in the spike as store-derived, for reference only.

Every option that shares computes the same number of derivations per update as createSelector ( for store-memo on that score update), so the work doesn't separate them. Their timings differ a bit by configuration, and no option is fastest everywhere. Correctness, memory, and API cost do separate them.

The recommendation: weakMemo

Read the stores in render, then call a derivation wrapped in weakMemo. It caches by the identity of its arguments, with objects in a WeakMap and primitives in a Map under them, like cache() on the server. When a snapshot is replaced, its entries are collected with it.

The code

In the benchmark that's one line at module scope, const getSharedCategoryStats = weakMemo(getCategoryStats), and a call in render:

  • Read the stores in render and pass the snapshots to the shared function.
  • Put the snapshot arguments first, so primitives are keyed under an object that gets collected.
  • The compiler still memoizes the call per instance, so the shared cache is only checked when a snapshot changes.

The explainer has a sandbox for this pattern. How React itself should share derived data is still open. A client cache() scoped to a render is the leading option, and weakMemo is the userland version the benchmarks measure.

Caveats

  • These are synthetic benchmarks. Each app is small and built to isolate one thing. There's no data from a real app yet.
  • Every result is from one machine and one browser. Whether the ratios carry over to other machines isn't tested.
  • Updates are timed inside flushSync, so they measure synchronous work. Only the typing benchmark measures what transitions do for responsiveness.
  • The wins depend on the React Compiler. Without it, use(store) loses wherever its readers re-render and the selector apps' don't (see the controls). In a partly compiled app, a reader the compiler doesn't cover re-renders its children.
  • Selection and subscribe churn in the main suite depend on the same-element bailout, which is its own PR, the first in the use(store) stack.
  • The use(store) variants follow the explainer's patterns, and the selector variants follow their libraries' docs. A selector app tuned by hand (for example, with a store per entity) does better, which is why the granular control has its own column.
  • The compiler doesn't memoize a value built across use() calls, because it flattens the scope that contains use(). Examples are an array filled with push(use(a)) or a loop that reads stores. A call on values read with use() is memoized.
  • The headline compares against idiomatic Redux Toolkit, and leaner Redux setups are faster in some configurations. The run that compares them with use(store) covers only rows. There, no verdict flips ( of ), but the other sizes aren't measured with leaner Redux.
  • The typing and memory benchmarks have far fewer samples than the main suite: keys per typing run and one measurement per memory run, over runs. Each table shows how many runs.

How the numbers were measured

The build

Every benchmark result on this page comes from one frozen React build: React (react-builds/head) as production bundles, with compiler build . The exception is the section without the same-element bailout, which uses the same commit with only that flag off. Each result file records the build it ran on, and this page's number check fails if any pinned file came from a different one. The libraries are Redux , react-redux , Redux Toolkit , Zustand , and Reselect . The browser is Chrome's headless shell on an , driven by Playwright from Node .

Timing and the ambient CPU gate

Each update is timed as one browser task inside flushSync, so every library renders synchronously and the selector work during dispatch is counted. The main suite has configurations: seven scenarios, at rows, with a CPU slowdown. Each configuration gets warm-up updates and then timed ones, with the order shuffled. Each configuration runs in browser restarts, except . Those got extra restarts because their first three disagreed close to parity, and two of the three headline losses are in them. The rule that every restart must agree (see how a win is decided) applies to all of their restarts. That's timed updates in the main suite.

Other work on the machine slows a benchmark down. So timing ran in small units behind a gate on ambient CPU, the cores used by processes outside the benchmark's own process tree. A unit started only when ambient CPU was at or below cores. It was thrown away and re-run if the mean during the unit was above . The frozen build has timing units. Ambient CPU is logged for every unit that ran under this gate, of them. Across those, the mean ambient CPU per unit was cores at the median and at most.

The load-average gate it replaced

It replaced a gate on the load average. Load includes the benchmark's own work, so that gate held back and threw away units because of the benchmark itself. Only the first restart of the main suite ran under it ( units). Every other restart and benchmark ran under the ambient gate.

How a win is decided

Verdicts compare average times. Differences within two standard errors are ties. Anything bigger counts as a win or a loss only if every browser restart agrees on which side is faster, and otherwise it's a tie too. A verdict like 1.4× faster means the other side's average time is that many times longer. The tables also show medians and spreads. A median can be lower on the side that's slower overall, when that side has more slow updates.

Each library is compared at its own faster compiler setting. So "the faster of Redux and Zustand" can be Zustand without the compiler in one configuration, and with it in the next.

Redux in the headline is idiomatic Redux, the setup the react-redux docs recommend: Redux Toolkit's configureStore and createSlice, with Immer's auto-freeze on, read through react-redux. Two leaner setups (a hand-written reducer, and auto-freeze off) are timed against it in the fairness controls. Even against the fastest of the three in each configuration, at rows, use(store) matches or beats Redux in of .

The counting build: what each update did

The counting build is a second build of the same code with counters. It counts renders of , not every component, with Row renders counted on their own too. It also counts selector calls and runs of an expensive derivation. It's deterministic, so it isn't timed or gated. Before any timing, each scenario replays updates in every variant, and the DOM must match after each one. That check runs in jsdom and in Chrome, except for the sweeps, which run it in Chrome only.

Notes for reading the scenarios

  • Add / remove (structure) is low-signal. Every variant re-renders every row, because the list's elements are new, so it mostly measures list reconciliation.
  • In the shared-derived-data benchmarks, a role update changes a user's role, and nothing renders users. The DOM never changes. use(store) does nothing for it, and those configurations are counted as "no work" instead of as a win.

The headline is lower than the last report's

On the last report's final build, use(store) matched or beat the faster of Redux and Zustand in of configurations. Two things changed since then. A review of the benchmark code found and fixed two places that were unfair to the selector libraries, and the React build changed too (the HostRoot redesign). By inspection, the fixes are the likely main cause, but neither change was isolated. The fixes:

  • The selector apps' rows had an extra selector for inline details in every scenario, even where the details are read in a child component. Now only the inline-details scenario uses a row with that selector.
  • Zustand computed the filter count in a selector, so the loop over every label ran on every update. Now it selects the labels and the filter and counts in render, like the other variants.

Both fixes remove work that only the selector apps were doing. Neither was timed on its own. The review also added the subscribe churn scenario, which mounts and unmounts readers. The fairer comparison is the one I stand behind, so it's the headline now.

  • ambient-cpu.mjs is the gate. It reports the CPU used by processes outside the benchmark's own process tree. The script waits for it before each unit, samples it during the unit, and logs it per unit.
  • node report-data.mjs computes every number on this page from the result files pinned in results/report-sources.json, and writes docs/use-store/data/bench-data.json. --check fails if regenerating would change anything.
  • node docs/use-store/tools/build-docs.mjs --pages=benchmark-report, from the repo root, builds this page from docs/use-store/src/benchmark-report.src.html. tools/check-docs.mjs runs the checks, including the one that fails on any digit in the prose that isn't generated.

The full matrix takes hours. Run it on a quiet machine, plugged in, with nothing heavy alongside.
