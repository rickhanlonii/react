What the three approaches are, and the ranges

The three approaches put the same state in different places:

  • One context (context) holds all the state in a useReducer at the root and passes it down through one Provider.
  • A context per slice (context-split) gives each slice of state its own Provider, and wraps rows in memo, the way people usually do.
  • use(store) (store) puts each entity in its own store, with small stores for the selection, the filter, the expanded rows, and the details.

Why the approaches differ

The timing mostly follows the renders. Where use(store) renders fewer rows and views, it wins by a lot.

The counting build shows the difference at rows. It counts renders of , not every component. Editing one entity re-renders row with use(store), and with one context or with a context per slice, because every row reads the entities. Changing the selection re-renders every row in all three (), because every row reads the selection.

Counted renders for every scenario
Why

Context re-renders every component that reads a context when the context's value changes. A context per slice narrows that to the consumers of the slice that changed. use(store) re-renders only the components that read the store that changed. The explainer covers the problem with Context and what re-renders.

Where all three render every row, the gaps are smaller, but they don't follow the render counts. With the compiler, use(store) is on add / remove against one context, with the same rows rendered.

The conditional reads are the exception. A context per slice re-renders as few rows and views as use(store) there, and use(store) is still faster: on the inline read with the compiler. When a context's value changes, React searches the tree below the Provider for its consumers. A store update goes straight to its readers (see what re-renders). I think that search is most of the difference, along with the root re-rendering to update its Providers on every change, but neither is profiled.

How typing was measured

The typing benchmark types into the filter while expensive rows re-filter in a transition. All three update the list in a transition, so React can interrupt the list render to handle the next key. One context also holds the input's value, so the urgent update for each key re-renders every row that reads the context.

Method and caveats

The method is the same as the benchmark report's. It uses one frozen React build and times behind a gate on ambient CPU, except for the main suite's first restart, which ran under the load-average gate it replaced. Verdicts compare means and need every browser restart to agree. The counting build counts renders of the rows and the shared views. The benchmark report's method section has the details.

  • These are synthetic benchmarks, with no data from a real app.
  • Timing uses the production build, and each update runs inside flushSync. Only the typing benchmark measures what transitions do for responsiveness.
  • Add / remove is low-signal, because it mostly measures list reconciliation.
  • The Context apps are written the usual way: one useReducer and Provider, or a Provider per slice with memo rows. A Context app tuned with more splitting or more memo could do better.
